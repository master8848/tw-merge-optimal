# Benchmark results

Recorded runs of `npm run bench` + `node bench/verify.mjs`. Rows: ops/s (higher is
better) or bytes; methodology in [docs/performance.md](../docs/performance.md).

## 2026-08-04 — object LRU caches + long-key flattening + both-cache-off rows (commit `6c69f2e` + bench)

Environment: Node v24.13.0, macOS 26.5.2, Apple Silicon (arm64), vitest v4.1.10.
Bundle: `bench/generated/tw-merge-optimal.mjs` regenerated by `bench_gen`
(962 classes, 258 families, family-guarded). tailwind-merge v3 from
`../tailwind-merge/dist/bundle-mjs.mjs` (both instances built once at module load).

The "(cache off)" rows disable tailwind-merge's LRU-500 via `cacheSize: 0`;
tw-merge-optimal's always-on 8,192-entry cache is disabled the same way via
`setCacheSize(0)` for its own "(cache off)" rows — worst case on both sides.

### History

The previous recorded run (commit `239fdea`, Map-LRU caches with a delete+re-set
touch) measured 1.19×/1.13×/1.09×/1.75× behind on the warm rows — that run was
also contaminated (machine load; a re-run of the same commit measured 1.06×/
1.005×/1.02×/1.10×). The object-LRU + flatten commit `6c69f2e` turns the warm
rows into 1.001–1.01× behind, parity or better: corpus is now **1.34–1.43× in
optimal's favor** (was 1.10× behind) and ultra-long is at parity (was 1.35×
behind). The cache-on vs cache-off rows widened from 9.2–9.5× to 12.3–12.8×;
with **both** caches off, tailwind-merge is 1.33–1.53× faster (its cold parse
path allocates less than the matcher-only runtime) — the always-on cache is
what carries the cold/dynamic win.
